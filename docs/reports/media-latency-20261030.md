# 2026-10-30 音视频延迟优化补充

用户明确将延迟与卡顿、清晰度并列为重点，并要求同时考虑固定滞后和逐渐积压。继续离线开发，不执行双机通话或入会验收。

## 最终改动

- 音频：采集/播放请求各 40ms，抖动缓冲初始 40ms、最小 20ms、最大预取 80ms、上限 160ms；20ms 分帧，保留回声消除和时钟/编解码器。声卡可能调整请求，未实测端到端音频延迟。
- 视频：通过 `onStreamPreCreate` 单独设初始/最小预取 0ms、最大预取 80ms、上限 200ms；最大预取至少为协商解码格式的一帧，避免 PJSIP 对过小值静默退回更大默认值。
- 发送：保留独立 RTP 发送线程，将 pacing 允许带宽设为 `max(编码上限, 3×平均码率)`，减少关键帧排队；这是短时发送节奏，不提高编码器平均/最高码率。PJSIP 自带阻塞发送模式也采用至少三倍平均码率的规则。
- 原生接收：交互模式将解码最小延迟参数从 100ms 改为 40ms，并优先保留最新已解码图像，防止慢消费者一直显示旧图。
- 修复实际触发的原生组帧错误：裁剪帧尾缺失包时，peek 索引由 `frm_pkt_cnt` 修正为 `frm_pkt_cnt-1`。旧下标检查了下一帧，可能把下一帧暂未到达的首包当成前一帧内容移除，后续到达也无法恢复，破坏 H.264 参考链。
- 兼容与回退：未改 SDP、JNI Java 接口或 MCU；保留既有视频释放补丁。`SIP_VIDEO_LATENCY_MODE=legacy` 恢复原生旧缓存策略，组帧下标修复始终保留。新 Windows 启动器选择 `SIP_MEDIA_PROFILE=legacy` 时，未显式指定原生模式则同时设为 legacy。

原生策略在流创建时读取进程环境，改环境变量需重启客户端；它不是 JVM `-D` 属性。直接运行 JAR 时，如需完整旧策略，须同时指定 legacy 媒体档和上述原生环境变量。没有通过关闭回声消除、禁用同步或新增 FEC/自适应码率换取低延迟。

## 合成接收验证

`scripts/test-media-latency.ps1` 调用真正的 OpenH264 编码器、RTP loop transport 和 PJMEDIA 视频流解码端口，不创建 SIP 会话、不打开摄像头/麦克风、不使用外部网络。
每组输入 1000 帧 320×180 合成 I420，编码成四切片 H.264；RTP 时钟 90000Hz。前 11 帧不计统计；乱序组在之后每帧交换前两个 RTP 包，共 989 帧发生帧内乱序。没有注入丢包或跨帧延迟。

比较同一修复后 SDK 的 legacy 和 interactive 策略，保持其他接收缓冲配置一致。输入为 15fps（当前 MCU 的名义输出帧率）及 25fps（客户端发送目标）；分别每 1、5、25 个输入帧读取一次解码输出。
滞后为当前输入 RTP 时间戳减输出画面 RTP 时间戳，按 90000Hz 换算；它是该接收组件的媒体时间滞后，不是 wall-clock 端到端通话延迟。

| 输入 | 消费节奏 | legacy 平均 / 最大 | interactive 平均 / 最大 | 正常与乱序 |
| --- | --- | --- | --- | --- |
| 15fps | 每 1 帧读取 | 200 / 200ms | 66.667 / 66.667ms | 均通过 |
| 15fps | 每 5 帧读取 | 200 / 200ms | 66.667 / 66.667ms | 均通过 |
| 15fps | 每 25 帧读取 | 200 / 200ms | 66.667 / 66.667ms | 均通过 |
| 25fps | 每 1 帧读取 | 160 / 160ms | 80 / 80ms | 均通过 |
| 25fps | 每 5 帧读取 | 200 / 200ms | 80 / 80ms | 均通过 |
| 25fps | 每 25 帧读取 | 200 / 200ms | 80 / 80ms | 均通过 |

合计 24 组通过；每组消费节奏分别有 989、197、39 个统计输出，全部无时间戳倒退、无重复时间戳。15fps 对应约 66.7 秒、25fps 对应 40 秒的输入媒体时间；测试加速执行，不是这些时长的真实通话。
合成数据中，这一接收组件的平均滞后降低约 50%–66.7%；不能外推为整通电话的延迟降低比例。原始 24 行结果见 [CSV](media-latency-20261030.csv)。

15fps 慢消费者/乱序用例在组帧修复前无法持续输出，修复后恢复全部应有输出；没有通过放宽这个用例的输出条件来掩盖解码问题。
测试没有测量像素画质、真实网络抖动/丢包、A/V 口型同步、设备延迟、MCU 编解码或最终 SDL/JavaFX 呈现。

## 原生构建与交付

隔离源码位于 `D:/work/.codex-execution/pjproject-latency-20261030`，基线为 PJSIP 2.17 的 `5a457451fa2712ba18e12b01738e8ff3af2b26fd`。
应用 `video-hangup-2.17.patch` 和 `video-latency-2.17.patch`，使用 MSYS2 GCC 16.2.0、SWIG 4.5.1、Windows JDK 17.0.20.1 重建静态库与 JNI。
原生重建脚本 `scripts/build-native-windows.ps1` 已实际复跑；它固定 `--host=x86_64-w64-mingw32` 并断言 `PJ_WIN64=1`，避免自动 configure 错认目标后产生 socket 句柄尺寸断言。
脚本保留已有配置，不执行 reset/clean 源码，不自动替换安装中的 DLL。最终边界修复后重建对应库并重链接 JNI，最终 DLL 指纹在主报告 JSON 和交付 manifest 中。

Windows 组包现在检查 x64 PE 类型和延迟策略构建标记，拒绝把旧原生库默默与新 Java 代码一起发布。原始 DLL、原始仓库工作区和已通过的 `83761e2` 便携包保留作回退，不提交新 DLL 二进制。

```powershell
pwsh -File scripts/build-native-windows.ps1 -PjSource 'D:\path\pjproject-2.17' -JdkHome 'C:\path\jdk17'
```
