# 答辩口径

老师高概率会问的几句，按这个答，不要现场加新架构。

## 视频优化做到哪里，能否说已经解决卡顿

2026-10-30 离线优化包括媒体档位、音频缓冲配置、设备能力快照、异步诊断日志、RTCP 统计，以及后台 ESL 字节帧和批量话单查询。默认发送目标为 848×480/25fps，1.2Mbps，上限 1.8Mbps；保留旧参数回退。没有修改既有 SDP、MCU Docker 或界面布局。

本机合成编码基准和原生参数读回通过，不能据此宣布双机或多人视频已流畅。当前 MCU 仍固定 960×540/15fps 九宫格，名义单格约 320×180，清晰度和帧率均受该配置约束。本轮按用户要求不做真实通话与入会验收，测试分母和未验证项见 [本轮报告](reports/media-backend-optimization-20261030.md)。

## SQLite 会不会太小，大规模是不是该上 MySQL

会。并发写很多、后台要开多实例、或要把 Kamailio 在线注册也落库时，MySQL/PostgreSQL 更合适。

课设没有这些前提。系统若变大，先撑爆的是 FreeSWITCH 混视频的 CPU 和每人一路 RTP，不是用户/CDR/文件那四张表。后台用 JPA，演示用 SQLite；用户量和 MCU 节点上去后只换连接串。Kamailio 的 REGISTER 继续放内存，重启后重新登录即可，不要和业务库绑在一起。

## 课件写了 JAIN SIP，为什么用 PJSIP

JAIN SIP 只做信令，没有 RTP 和编解码。课件第 7 页就点名 PJSIP 的 Java 绑定做音视频。我们用 PJSUA2 补媒体，报告里对比 JAIN 即可，不必再接一套纯 Java 协议栈。

## 为什么 6–8 人要 FreeSWITCH，一对一却不进 MCU

PJSIP 视频拼接默认约 4 格，miniSIPServer 会议室最多 5 人。6–8 人必须有会议焦点，每人只打一路进房间。一对一走 Kamailio 直连，延迟低、不占混流 CPU。

## 为什么是 JavaFX 窗口，不是网页

课件要 Java PC 客户端，验收两台电脑。Kamailio/PJSIP/FreeSWITCH 都不带 IM 界面。网页只做管理查询；通话不要改成 WebRTC 浏览器。
